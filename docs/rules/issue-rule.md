# Issue Rule

## 1. 문서 목적

GitHub Issue를 생성할 때 남겨야 할 필수 항목과, 만들어진 Issue를 언제 다시 꺼내 해소할지 판단하는 절차를 정의한다.

Issue를 "언제 GitHub Issue로 분리할지"(Task/PR 범위 판단)는 `docs/rules/task-rule.md` §4-2를 따른다. 이 문서는 그 이후 — 실제로 Issue를 어떻게 작성하고, 언제 다시 점검하는지를 다룬다.

---

## 2. Issue 제목

- 라벨/태그 접두어 없이, 증상을 완전한 문장으로 서술한다.
  - 예: "재계산 완료 신호가 API에 없어 저장 직후 목록 캐시가 stale 상태로 갱신됨"
- 원인이나 해결 방향은 제목에 넣지 않는다 (본문에서 다룬다). 제목만 보고 무엇이 문제인지 파악할 수 있어야 한다.

---

## 3. Issue 본문 필수 항목

| 섹션 | 내용 | 생략 가능 조건 |
|---|---|---|
| 문제/배경 | 무엇이 어떻게 잘못됐는지, 어떤 계기로 발견했는지 (예: "Codex 리뷰 PR #32에서 지적") | 없음 (필수) |
| 원인 | 코드 레벨에서 왜 발생하는지 | 원인 파악 전이면 "원인 미파악"으로 명시하고 생략하지 않는다 |
| 재현 조건 | 재현 절차 | 버그가 아니라 설계 불일치/기술부채면 생략 가능 |
| 관련 파일 | `path/to/File.java:12-34` 형식으로 실제 코드 위치 | 없음 (필수) |
| 제안 방향 | 해결 방향 초안 | 결정된 설계가 아님을 명시. 방향이 불확실하면 생략 가능 |
| 관련 PR/Task | 발견된 계기가 된 PR/Task 번호 | 없음 (필수, 신규 발견이면 "신규 발견"으로 명시) |

---

## 4. 라벨

### Type 라벨 (1개, 필수)

| 라벨 | 기준 |
|---|---|
| `bug` | 기존 동작이 잘못됨 |
| `tech-debt` | 동작은 맞지만 구조/일관성 문제 |
| `design-gap` | 설계 문서(Notion) 자체의 누락/불일치 |

### Part 라벨 (1개 이상, 필수)

`backend` / `frontend` / `ai-worker` / `infra` / `docs`

심각도는 별도 라벨을 두지 않는다. 심각도 판단은 5절의 점검 시점에 상황을 보고 그 자리에서 한다 — 생성 시점에 라벨로 고정하면 이후 상황 변화(다른 버그의 발견, 우선순위 변화)를 반영하지 못한다.

---

## 5. Issue 해소 시점 점검

새 브랜치를 생성하기 전(`docs/rules/git-rule.md` §6), 아래 순서로 open issue를 점검하고 사용자에게 결과를 보고한다.

1. `gh issue list --state open`으로 목록을 확인한다.
2. 이번에 만들 브랜치/Task의 Part 라벨과 겹치는 이슈가 있는지 확인한다.
3. 겹치는 이슈가 있으면 사용자에게 보고하고, 아래 중 하나로 결정한다.
   - **이번 Task에 포함**: Task 파일의 `작업 항목`에 추가
   - **별도로 먼저 해결**: 이번 Task와 분리해 별도 브랜치/Task로 선처리
   - **보류**: 사유를 이슈 코멘트로 남기고 다음 점검 때 다시 판단
4. Part가 겹치지 않아도 `bug` 라벨이고 실사용 영향이 크다고 판단되면 무관하게 같이 보고한다.
5. 점검 결과 "관련 이슈 없음"이어도 점검했다는 사실은 짧게 보고한다 — 점검을 건너뛴 것과 구분하기 위함.

---

## 6. 금지 규칙

- Type/Part 라벨 없이 Issue를 생성하지 않는다.
- 관련 파일 위치 없이 "어딘가 이상하다" 식으로 Issue를 생성하지 않는다.
- 브랜치 생성 전 open issue 점검을 건너뛰지 않는다.
