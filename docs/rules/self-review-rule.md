# Self Review Rule

## 1. 문서 목적

코드 완료 후 파트 무관하게 공통으로 수행하는 검토 기준을 정의한다.
파트별 세부 검토는 각 파트의 Review Rule에서 담당한다.

---

## 2. 공통 검토 항목

### Done Condition 충족 여부

- Task 파일의 Done Condition 항목을 모두 충족했는가?
- 충족하지 못한 항목이 있다면 작업을 완료로 보지 않는다.

### Out of Scope 침범 여부

- Task 파일의 Out of Scope 항목을 침범하지 않았는가?
- 범위 외 변경이 포함되었다면 해당 변경을 되돌리거나 사용자에게 확인한다.

### 아키텍처 경계 위반 여부

- AI Worker가 DB에 직접 접근하지 않는가?
- AI Worker가 점수 계산, 상태 변경, 저장을 수행하지 않는가?
- 모든 API 응답이 공통 Wrapper `{ header, data }`를 사용하는가?
- 설계 문서 없이 도메인 구조를 임의로 변경하지 않았는가?

---

### 테스트 통과 여부

- `./gradlew test` (Spring Boot) 또는 파트별 테스트 명령이 통과하는가?
- 조건 분기, 계산, 상태 전이 로직이 있다면 단위 테스트가 작성되었는가?
- 테스트를 생략한 경우, 단순 CRUD/설정/Mapper 중 하나에 해당하는가?

---

## 3. 검토 순서

1. Done Condition 체크 → 미충족 항목이 있으면 작업 재개
2. Out of Scope 체크 → 침범 항목이 있으면 되돌리거나 사용자 확인
3. 아키텍처 경계 체크 → 위반 항목이 있으면 즉시 수정
4. 테스트 통과 체크 → 실패하면 수정 후 재검증
5. 파트별 Review Rule 수행
6. 미해결 발견사항 처리 (4절 참고)

---

## 4. 미해결 발견사항 처리

작업 중 문제를 발견했지만(자체 QA, Codex 리뷰 등 발견 주체는 무관하다) 이번 작업 범위에서 바로 고치지 않기로 판단했다면, 그 사실을 기억이나 대화 로그에만 남기지 않는다. Notion 로그나 로컬 메모리는 "이런 일이 있었다"를 남길 뿐 "이거 해야 한다"를 추적하지 못하고, 다른 PC/다른 세션에서는 보이지 않는다.

- **GitHub Issue로 등록한다.** 이 저장소에서 세션·PC와 무관하게 항상 보이는 유일한 트래커다.
- 등록 전 반드시 사용자에게 제목/본문 초안을 보여주고 확인받는다 — 확인 없이 임의로 생성하지 않는다.
- Issue 본문에는 최소한 다음을 포함한다:
  - 문제 설명 (무엇이, 왜 문제인지)
  - 왜 지금 고치지 않았는지 (범위 밖 / 우선순위 낮음 / 추가 조사 필요 등)
  - Next Step (체크리스트)
  - 관련 PR/커밋 링크
- Notion 07번 AI 워크플로우 로그에 남길 만한 사건이면(기록 기준은 해당 문서 참고) 그쪽에도 기록하되, Issue 번호를 함께 적어 상호 참조되게 한다.
