# Flyway DB Migration Rule

## 1. 문서 목적

이 문서는 Java + Spring Boot + Flyway 프로젝트에서 DB 마이그레이션을 관리하는 규칙을 정의한다.

---

## 2. 핵심 패턴 요약

- 마이그레이션 파일명은 `V{숫자}__설명.sql` 형식을 사용한다.
- 마이그레이션 파일은 `src/main/resources/db/migration` 아래에 둔다.
- JPA는 `ddl-auto: validate`로 두고, 스키마 변경 기준은 Flyway SQL로 둔다.
- 컬럼 추가 시 기본값, 데이터 보정, 인덱스/유니크 제약 필요 여부를 같은 변경 흐름 안에서 함께 검토한다.
- 제약조건과 인덱스는 이름을 명시적으로 붙인다.

---

## 3. 기본 설정 규칙

### 3-1. Flyway 위치

마이그레이션 파일은 다음 위치를 기본으로 한다.

- `src/main/resources/db/migration`

### 3-2. JPA와 스키마 변경 기준

스키마 생성과 변경의 기준은 JPA가 아니라 Flyway 마이그레이션이다.

권장 설정:

- `spring.flyway.enabled=true`
- `spring.flyway.locations=classpath:db/migration`
- `spring.jpa.hibernate.ddl-auto=validate`

즉, 엔티티 변경만으로 DB를 바꾸지 않고, DB 구조 변경은 SQL 마이그레이션으로 반영한다.

---

## 4. 파일 네이밍 규칙

마이그레이션 파일명은 다음 형식을 따른다.

- `V1__init.sql`
- `V2__add_company_profile.sql`
- `V6__refactor_bid_analysis_schema.sql`

규칙:

- 버전은 `V{정수}` 형식을 사용한다.
- 버전 뒤에는 `__`를 사용한다.
- 설명은 소문자와 언더스코어 기준으로 작성한다.
- 설명은 변경 목적이 드러나게 짧게 적는다.

하나의 버전 번호를 재사용하지 않는다.

---

## 5. 파일 분리 규칙

### 5-1. 초기 스키마

초기 테이블 생성은 init 성격의 마이그레이션 파일에서 정의한다.

허용 대상:

- 핵심 테이블 생성
- 기본 제약조건 생성
- 기본 인덱스 생성

### 5-2. 이후 변경

초기화 이후에는 변경 목적 단위로 새 버전 파일을 추가한다.

이미 적용된 파일을 수정하는 대신 새 버전 파일을 추가한다.
테스트 DB, 로컬 개발 DB를 포함해 한 번이라도 적용된 마이그레이션은 동일한 기준으로 취급한다.

---

## 6. 스키마 변경 작성 규칙

### 6-1. 명시적 SQL 사용

권장 방식:

- `CREATE TABLE`
- `ALTER TABLE`
- `CREATE INDEX`
- `CREATE UNIQUE INDEX`
- `ADD CONSTRAINT`
- 필요 시 `UPDATE`를 통한 기존 데이터 보정

### 6-2. 컬럼 추가 패턴

새 컬럼을 추가할 때는 그 컬럼이 실제로 사용 가능해지기 위해 필요한 후속 작업을 함께 검토한다.

함께 고려할 항목:

- `NULL / NOT NULL`
- 기본값 설정
- 기존 데이터 보정
- 조회 인덱스 추가
- 유니크 제약 추가

단, 대량 데이터 보정이나 운영 부담이 큰 작업은 별도 마이그레이션으로 분리할 수 있다.

### 6-3. 리팩터링 수준 변경

테이블 구조를 크게 바꾸는 변경은 별도 버전 파일로 분리한다.
구조 리팩터링은 일반 컬럼 추가와 같은 파일에 무분별하게 섞지 않는다.

---

## 7. 제약조건과 인덱스 규칙

제약조건과 인덱스에는 이름을 명시적으로 붙인다.

규칙:

- PK, FK, UK, CHECK, INDEX 이름을 생략하지 않는다.
- 접두어는 프로젝트 안에서 일관되게 유지한다.
- 조회 패턴이 분명한 컬럼에는 인덱스를 함께 검토한다.
- FK, 기간, 상태 조합처럼 실제 조회 조건에 자주 쓰이는 조합은 복합 인덱스를 고려한다.

---

## 8. 데이터 보정 규칙

기존 데이터와 충돌할 수 있는 변경은 스키마 변경과 함께 데이터 보정 필요 여부를 검토한다.

단, 데이터 양이 많거나 락/부하 영향이 큰 보정은 별도 마이그레이션이나 운영 절차로 분리할 수 있다.

---

## 9. 금지 규칙

- 엔티티 변경만으로 DB 스키마가 바뀌길 기대하지 않는다.
- 이미 배포된 마이그레이션 파일을 수정하지 않는다.
- 테스트나 로컬 실행에서 이미 적용된 마이그레이션 파일을 되돌아가 수정하지 않는다.
- 제약조건이나 인덱스 이름을 생략하지 않는다.
- 큰 구조 리팩터링과 사소한 컬럼 추가를 한 파일에 무분별하게 섞지 않는다.

---

## 10. 한 줄 요약

- 스키마 변경 기준은 JPA가 아니라 Flyway SQL이다.
- 마이그레이션은 `V{n}__description.sql` 형식으로 누적한다.
- 초기 스키마와 이후 변경 파일을 분리한다.
- 컬럼 추가 시 기본값, 데이터 보정, 인덱스/제약 필요 여부를 함께 검토한다.
- 제약조건과 인덱스는 이름을 명시하고, 명명 규칙은 일관되게 유지한다.
