# Transaction Rule

## 1. 문서 목적

이 문서는 서비스, 배치, 장기 실행 작업에서 사용하는 트랜잭션 설계 규칙을 정의한다.

---

## 2. 핵심 패턴 요약

- 서비스 메서드 단위로 읽기 트랜잭션과 쓰기 트랜잭션을 명시적으로 분리한다.
- 여러 Repository 호출이 하나의 업무 결과를 만들어야 하면 하나의 쓰기 트랜잭션으로 묶는다.
- 장기 실행 작업 전체를 하나의 트랜잭션으로 감싸지 않고, 선점 단계와 실행 단계를 분리한다.
- 스케줄러, 실행 조정 서비스, 작업 래퍼는 트랜잭션을 직접 잡지 않고 호출 순서만 제어한다.
- 실패는 예외를 전파해 현재 트랜잭션을 롤백시키고, 실패 처리와 로깅은 트랜잭션 바깥 실행 래퍼에서 담당한다.
- 동시성 충돌처럼 흡수 가능한 상황은 예외 대신 빈 결과나 0건 업데이트로 표현하고 다음 단계 진입을 막는다.

---

## 3. 서비스 계층 트랜잭션 규칙

### 3-1. 쓰기 유스케이스

생성, 상태 변경, 저장, 다중 Repository 조합이 발생하는 메서드는 `@Transactional`로 묶는다.

하나의 쓰기 트랜잭션으로 묶어야 하는 대상:

- 선행 검증용 조회
- 엔티티 생성 또는 수정
- 다중 Repository 저장
- 최종 상태 확정

### 3-2. 읽기 유스케이스

조회 전용 메서드는 `@Transactional(readOnly = true)`를 명시한다.

적용 대상: 상세 조회, 목록 조회, 검색 조회, 읽은 결과를 DTO로 조합하는 조회

읽기 트랜잭션 안에서는 다음을 하지 않는다.

- 저장
- 상태 변경
- 벌크 update
- 변경 감지에 의존한 엔티티 수정
- flush 결과 기대

---

## 4. 여러 Repository 호출을 묶는 규칙

하나의 유스케이스에서 여러 Repository를 호출하더라도 결과가 하나의 업무 단위라면 Service가 이를 하나의 트랜잭션으로 묶는다.

트랜잭션 경계는 Repository가 아니라 Service 또는 Processor 메서드에 둔다.
Repository는 개별 영속성 작업만 수행하고, 트랜잭션 조합 책임은 상위 계층이 가진다.

---

## 5. 장기 실행 작업 트랜잭션 규칙

### 5-1. 작업 전체를 하나로 묶지 않는다

스케줄러, JobRunner, 작업 Service, 실행 조정 계층은 트랜잭션을 잡지 않는다.
이 계층은 실행 조건 확인, 시작/종료 로깅, 예외 래핑, 단계 호출 순서 제어만 담당한다.

### 5-2. 선점 단계와 실행 단계를 분리한다

1. 선점 단계: 대상 조회 → 현재 상태를 조건으로 한 상태 변경 → 선점 실패 시 빈 결과 반환
2. 실행 단계: 작업 단위 생성 → source 데이터 조회 → 계산/조합/저장 → 최종 상태 변경

선점과 실제 실행은 별도 쓰기 트랜잭션으로 분리한다.

---

## 6. 실패와 롤백 규칙

### 6-1. 쓰기 트랜잭션 내부 실패

예외가 발생하면 예외를 삼키지 않고 그대로 전파한다.

예외를 던져야 하는 경우:
- 필수 선행 데이터가 없을 때
- 계산 결과가 내부 불일치 상태일 때
- 중간 단계 이후 후속 필수 단계가 성립하지 않을 때

### 6-2. 실패 처리 위치

실패 로깅, 에러 코드 래핑, 후처리 통지는 트랜잭션 메서드 바깥 실행 래퍼에서 담당한다.

### 6-3. 예외를 던지지 않는 실패

동시성 충돌이나 선점 실패는 예외보다 빈 ID 목록 반환, 벌크 update 결과 0건 반환으로 표현하고 다음 단계 실행을 중단한다.

---

## 7. 상태 변경과 트랜잭션 규칙

- 현재 상태를 where 조건에 포함한다.
- 상태 변경과 후속 저장은 같은 쓰기 트랜잭션 안에서 확정한다.
- 상태 변경 실패를 허용한 채 후속 저장을 계속 진행하지 않는다.

---

## 8. 참조 엔티티와 트랜잭션 규칙

트랜잭션 안에서 연관 엔티티 전체 조회가 필요 없고 FK 연결만 필요하면 `EntityManager.getReference()` 사용을 허용한다.
단, 참조 대상이 이미 선행 단계에서 확정되었고 추가 조회가 필요 없을 때만 사용한다.

---

## 9. 외부 연동과 트랜잭션 규칙

외부 API 호출, 파일 업로드 같은 네트워크 I/O는 긴 쓰기 트랜잭션 안에 오래 유지하지 않는다.

---

## 10. 금지 규칙

- 조회 메서드를 쓰기 트랜잭션으로 열어 두지 않는다.
- 읽기 트랜잭션 안에서 저장이나 상태 변경을 수행하지 않는다.
- 장기 실행 작업 전체를 하나의 긴 트랜잭션으로 감싸지 않는다.
- 트랜잭션 내부에서 예외를 로그만 남기고 삼키지 않는다.
- 동시성 경쟁 상황과 실제 실패를 같은 방식으로 처리하지 않는다.
- Repository에 트랜잭션 조합 책임을 두지 않는다.
- `@Transactional`/`@Async` 메서드를 같은 클래스 내부에서 직접 호출(self-invocation)하지 않는다.
- 커밋 이후에만 실행돼야 하는 비동기 작업을 `@Transactional` 메서드 안에서 다른 클래스의 `@Async` 메서드로 직접 호출하지 않는다 (커밋 전 데이터를 읽을 수 있음 — `AFTER_COMMIT` 이벤트 리스너로 대체한다).

---

## 11. AOP 프록시와 Self-Invocation 규칙

`@Transactional`, `@Async`는 Spring이 생성하는 프록시를 거쳐야 적용된다. 같은 클래스 내부에서 `this.method()` 형태로 직접 호출하면 프록시를 우회해, 원래 의도한 트랜잭션 경계나 비동기 실행 없이 호출자와 같은 스레드에서 그대로 동기 실행된다.

- 트랜잭션 경계나 비동기 실행이 필요한 메서드는 호출자와 다른 클래스(별도 Service/컴포넌트)로 분리한다.
- 같은 클래스 안에서 `@Transactional`/`@Async` 메서드를 직접 호출하지 않는다.
- 부득이하게 같은 클래스 안에서 호출해야 한다면 self-injection(자기 자신을 프록시로 주입)보다 책임 분리를 우선 검토한다.
- `@Async` 메서드가 실제로 별도 스레드에서 실행되는지 로그의 스레드 이름으로 확인한다. 호출자와 동일한 스레드 이름이 찍히면 프록시가 적용되지 않은 것이다.

---

## 12. 트랜잭션 커밋 이후 비동기 후속 작업 트리거 규칙

`@Transactional` 메서드 안에서 다른 클래스의 `@Async` 메서드를 호출하면, self-invocation(§11)이 아니어도 문제가 생길 수 있다. `@Async`는 실행 스레드만 전환할 뿐 트랜잭션을 스스로 만들지 않지만, 스레드가 바뀌면 트랜잭션 컨텍스트를 이어받지 못해 그 안에서 실행되는 `@Transactional` 코드는 새 트랜잭션을 시작한다. 호출자의 트랜잭션이 아직 커밋 전이면, 새로 시작된 트랜잭션은 그 변경을 보지 못하고 이전 상태를 읽을 수 있다.

- 트랜잭션 커밋 이후에만 시작해야 하는 비동기 후속 작업은 서비스 메서드를 직접 호출하지 않는다.
- 대신 도메인 이벤트를 발행하고, `@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)`와 `@Async`를 함께 붙인 리스너에서 처리한다. `@TransactionalEventListener`만 있으면 커밋 직후 호출자와 같은 스레드에서 동기 실행돼 블로킹되므로 둘 다 필요하다.
- 이벤트 발행 시점에 활성 트랜잭션이 없으면 `@TransactionalEventListener`는 기본적으로 실행되지 않는다 (필요하면 `fallbackExecution = true`). 트랜잭션이 롤백되면 실행되지 않는다 — `@Transactional` 테스트는 기본적으로 종료 시 롤백하므로 `@Commit` 등 별도 처리 없이는 테스트에서 검증할 수 없다.
- 이벤트 타입은 사건마다 별도 클래스로 정의한다. 스프링은 이벤트 객체의 타입으로 리스너를 매칭하므로, 같은 타입을 여러 사건에 재사용하면 의도치 않은 리스너까지 호출된다.
- 비동기 메서드 자신이 여러 건의 쓰기를 수행한다면 §3-1 기준대로 명시적 `@Transactional`을 별도로 붙인다 — 그러지 않으면 각 쓰기가 개별 커밋되어 중간 실패 시 일부만 저장될 수 있다.

참고 구현: `BidNoticeProcessor.process()`(이벤트 발행) → `BidNoticeCollectedEvent` → `BidMatchEventListener.handle()`(`@Async` + `@TransactionalEventListener(phase = AFTER_COMMIT)`).

## 13. Hibernate 쓰기 지연과 실행 순서 규칙

영속성 컨텍스트는 Repository 메서드를 호출한 코드 순서가 아니라, 액션 타입별로 정해진 내부 순서(기본적으로 insert → update → delete)로 SQL을 모아 flush한다. 그래서 트랜잭션 안에서 코드상 실행 순서와 실제 DB 실행 순서가 어긋날 수 있다.

이 어긋남이 결과에 영향을 주는 대표 상황:

- 삭제 후 같은 제약(UNIQUE 등)에 걸리는 데이터를 다시 삽입하는 경우 — insert가 delete보다 먼저 나가 제약 위반이 발생할 수 있다.
- 같은 트랜잭션 안에서 앞선 변경을 전제로 native query나 벌크 update를 실행하는 경우.
- 앞선 쓰기 결과를 같은 트랜잭션 안에서 곧바로 조회해 사용하는 경우.

실행 순서가 결과에 영향을 주는 지점에서는 순서를 영속성 컨텍스트의 내부 처리에 맡기지 않고, 그 지점 앞뒤로 명시적 `flush()`를 호출해 실행 순서를 강제한다. 순서가 결과에 영향을 주지 않는 일반적인 저장/수정에는 불필요한 flush를 남발하지 않는다.

---

## 14. 한 줄 요약

- 쓰기 유스케이스는 Service/Processor 메서드 단위 `@Transactional`로 묶는다.
- 조회 유스케이스는 `@Transactional(readOnly = true)`를 명시한다.
- 여러 Repository 호출은 유스케이스 기준으로 하나의 트랜잭션으로 묶는다.
- 장기 실행 작업은 선점 트랜잭션과 실행 트랜잭션을 분리한다.
- 실패는 예외 전파로 롤백시키고, 경쟁 실패는 빈 결과나 0건 업데이트로 흡수한다.
- `@Transactional`/`@Async` 메서드는 같은 클래스 내부에서 직접 호출하지 않는다 (self-invocation 시 프록시 우회, 동기 실행됨).
- 트랜잭션 커밋 이후에만 시작해야 하는 비동기 후속 작업은 직접 호출 대신 도메인 이벤트 + `@TransactionalEventListener(AFTER_COMMIT)` + `@Async` 조합으로 트리거한다.
- 실행 순서가 결과에 영향을 주는 영속성 작업(제약조건이 걸린 삭제 후 재삽입 등)은 명시적 `flush()`로 순서를 강제한다.
