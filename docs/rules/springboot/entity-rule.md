# Entity Rule

## 1. 문서 목적
- JPA 엔티티 설계에 대한 프로젝트 공통 규칙을 정의한다.
- 엔티티 생성, 상태 변경, 매핑, 연관관계, DTO 경계를 일관되게 유지한다.
- 이 문서는 구현 설명서가 아니라 설계 규칙 문서다.

## 2. 엔티티 기본 원칙
- 엔티티는 DB 테이블 매핑 객체이면서 도메인 상태를 보유하는 객체로 설계한다.
- 엔티티는 영속성 편의를 위한 단순 데이터 묶음으로만 두지 않는다.
- 엔티티는 공통 베이스 엔티티를 상속해 `id`, 감사 컬럼을 공통화한다.
- 엔티티 필드는 컬럼명과 주요 제약(nullable, 길이, 정밀도 등)을 필요한 범위에서 명시한다.
- 엔티티는 기술용 보일러플레이트보다 도메인 상태와 규칙이 드러나게 작성한다.
- 닫힌 상태값은 문자열이 아니라 enum으로 표현한다.
- 값 객체를 도입할 때는 의미와 불변식이 있을 때만 사용하고 매핑 방식을 명시한다.

## 3. 생성과 상태 변경 규칙
- 엔티티 생성은 의미 있는 생성 경로(정적 팩토리 메서드 또는 빌더)를 기본으로 하되, JPA가 요구하는 생성 제약을 함께 만족시킨다.
- 생성 시점에 만족해야 하는 불변식은 생성자 또는 정적 팩토리 메서드에서 검증한다.
- 생성 시 필수인 식별자, 이름, 코드 같은 값에 `0`, `""`, `Instant.EPOCH` 같은 센티널 기본값을 공개 생성 경로에 두지 않는다.
- 공개 생성 경로는 도메인상 유효한 값만 받도록 설계하고, 필수값 누락이 컴파일 단계 또는 생성 시점 검증에서 드러나게 한다.
- JPA 무인자 생성자 요구사항은 `@NoArgsConstructor(access = AccessLevel.PROTECTED)` (Lombok)로 해결한다.
- JPA 편의를 위한 생성 경로를 외부 애플리케이션 코드가 직접 사용하게 두지 않는다.
- 기본값은 도메인 기본 상태가 명확한 경우에만 허용한다. 예: `active = true`, `status = PENDING`, `revoked = false`
- 상태 변경은 필드 직접 노출(public setter)보다 목적이 드러나는 메서드로 수행한다.
- 상태 변경 메서드는 변경 가능 조건을 먼저 검증한 뒤 필드를 갱신한다.
- 상태 전이 메서드는 관련 필드를 함께 갱신한다.
- 상태 전이 메서드는 이미 처리된 상태를 다시 처리하지 못하게 막는 것을 기본 원칙으로 한다.
- 승인, 거절, 인증 완료처럼 단방향 처리 성격의 메서드는 재호출 시 예외가 나도록 설계한다.
- 상태 전이 시 상태값만 바꾸지 말고 처리 시각, 처리 주체처럼 함께 움직여야 하는 필드를 같은 메서드 안에서 갱신한다.
- 계산 가능하지만 DB가 관리하는 값은 읽기 전용 컬럼으로 다룬다.

## 4. JPA 매핑 규칙
- 모든 엔티티는 `@Entity`와 `@Table(name = ...)`를 명시한다.
- 기본 키는 공통 베이스 엔티티에서 관리하고 외부에서 임의 변경하지 못하게 한다.
- 컬럼은 `@Column`으로 이름과 제약을 명시한다.
- enum은 반드시 `@Enumerated(EnumType.STRING)`을 사용한다.
- 감사 컬럼은 공통 베이스 엔티티에서 관리한다.
- DB가 계산하거나 트리거로 관리하는 컬럼은 `insertable = false, updatable = false`로 읽기 전용 매핑한다.
- 값 객체를 엔티티에 포함할 때는 `@Embeddable`, `@Embedded` 또는 컨버터 등 명시적 매핑을 사용한다.

## 5. 연관관계 규칙
- 연관관계는 필요한 최소 범위만 매핑한다.
- 기본은 `@ManyToOne(fetch = FetchType.LAZY)`를 사용한다.
- `@JoinColumn`에는 컬럼명, nullable, foreign key 이름을 명시한다.
- 양방향 연관관계와 컬렉션 연관관계는 실제 탐색 필요가 있을 때만 추가한다.
- `@OneToMany`는 기본 매핑으로 두지 않고, 컬렉션 탐색이 실제로 필요한 경우에만 제한적으로 사용한다.
- FK 값을 조회 조건이나 응답 조합에서 자주 써야 하면 읽기 전용 FK 컬럼을 별도로 둘 수 있다.
- `@ManyToMany`는 기본 선택지로 사용하지 않는다.
- N:N 관계는 연결 엔티티를 별도로 만들고 `@ManyToOne` 2개로 모델링하는 방식을 우선 사용한다.
- 연결 엔티티의 기본 키는 별도 단일 PK를 우선 사용하고, 관계 유일성은 unique constraint로 보장한다.
- 연관관계 편의 메서드는 양쪽 관계 일관성이 꼭 필요할 때만 최소한으로 둔다.

## 6. 엔티티와 DTO 경계 규칙
- 엔티티를 API 요청/응답 DTO로 직접 사용하지 않는다.
- DTO 변환은 엔티티 내부가 아니라 mapper 또는 별도 변환 계층에서 수행한다.
- Request DTO가 엔티티를 직접 상속하거나 포함하지 않게 한다.
- Response DTO는 엔티티 전체를 그대로 노출하지 않고 필요한 값만 선택한다.
- 엔티티 내부에 API 응답 생성 로직을 넣지 않는다.

## 7. 금지사항
- 엔티티에 `@Data` (Lombok) 또는 equals/hashCode를 모든 필드로 생성하는 행위
- enum을 `ORDINAL`로 저장하는 행위
- 엔티티를 Controller 응답으로 직접 반환하는 행위
- 모든 연관관계를 무조건 양방향으로 매핑하는 행위
- 상태 검증 없이 필드를 여기저기서 직접 변경하는 행위 (무분별한 public setter)
- DB 계산 컬럼을 애플리케이션에서 임의로 덮어쓰는 행위
- JPA 무인자 생성자 외부 접근을 허용하는 행위
- 이미 처리된 상태 전이 메서드를 반복 호출해도 통과되도록 두는 행위
- 상태 전이 시 관련 감사 필드나 처리 필드를 누락한 채 상태값만 바꾸는 행위
- `@ManyToMany`를 단순 편의만으로 직접 매핑하는 행위

## 8. 체크리스트
- 엔티티가 공통 베이스 엔티티를 통해 식별자와 감사 컬럼을 관리하는가?
- JPA용 무인자 생성자가 `PROTECTED`로 제한되어 있는가?
- 상태 변경이 목적 있는 메서드로 표현되는가?
- 상태 전이 메서드가 재처리 금지 규칙을 검증하는가?
- 상태 전이 시 함께 갱신돼야 하는 처리 필드가 같은 메서드에서 빠짐없이 갱신되는가?
- 컬럼 제약과 enum 저장 방식이 명시되어 있는가?
- 연관관계가 최소 범위, LAZY, 명시적 `@JoinColumn` 기준으로 설계되었는가?
- 엔티티와 DTO 변환이 엔티티 밖에서 이뤄지는가?
- N:N 관계를 `@ManyToMany` 대신 연결 엔티티 중심으로 모델링했는가?
