# Security Rule

## 1. 문서 목적

이 문서는 Java + Spring Boot 프로젝트에서 사용할 수 있는 보안, 인증, 인가의 기본 원칙을 정의한다.
특정 인증 방식이나 라이브러리 세부 구현을 강하게 전제하지 않고, 재사용 가능한 공통 규칙만 다룬다.

---

## 2. 인증과 인가를 구분한다

인증과 인가는 서로 다른 책임으로 다룬다.

- 인증: 요청 주체가 누구인지 확인하는 과정
- 인가: 인증된 주체가 어떤 자원이나 기능에 접근할 수 있는지 판단하는 과정

즉, 로그인 여부 확인과 권한 판단을 하나의 개념으로 섞지 않는다.

---

## 3. 민감정보 처리 원칙

다음 정보는 민감정보로 취급한다.

- 비밀번호
- 토큰
- 시크릿 키
- API 키
- 인증 세션 식별자
- 외부 인증 연동 비밀값

규칙:

- 민감정보를 코드에 하드코딩하지 않는다.
- 민감정보를 로그에 남기지 않는다.
- 민감정보를 예외 메시지나 응답 본문에 노출하지 않는다.
- 비밀번호 원문을 저장하지 않는다.
- 토큰이나 시크릿 전체 값을 디버그 출력하지 않는다.

즉, 민감정보는 저장, 출력, 전달 모든 단계에서 최소 노출을 원칙으로 한다.

---

## 4. 최소 권한 원칙

모든 요청은 기본적으로 보호 대상이라고 가정한다.
공개가 필요한 엔드포인트만 예외적으로 연다.

규칙:

- `permitAll`은 꼭 필요한 공개 엔드포인트에만 적용한다.
- 인증만 필요하고 권한 구분이 없는 경우와, 역할/권한 검사가 필요한 경우를 분리한다.
- 권한은 업무에 필요한 최소 범위만 부여한다.
- 관리자 권한이나 광범위 권한을 기본값으로 사용하지 않는다.

즉, 기본은 차단이고 필요한 경로만 명시적으로 허용한다.

---

## 5. 보안 설정과 비즈니스 로직을 분리한다

보안 설정은 인증 방식, 요청 보호 범위, 기본 접근 정책을 담당한다.
비즈니스 로직은 업무 규칙과 도메인 처리를 담당한다.

규칙:

- 인증 방식 결정과 필터 구성은 보안 설정 계층에 둔다.
- 공개/보호 엔드포인트 구분과 기본 접근 정책은 보안 계층에서 정의한다.
- 업무 규칙, 도메인 상태 판단, 데이터별 권한 판단을 보안 설정에 넣지 않는다.
- 인증 수단이 JWT인지 세션인지에 따라 비즈니스 로직이 달라지지 않게 한다.

---

## 6. 보안 정보 전달 원칙

Controller와 Service는 보안 구현 세부를 직접 알지 않게 한다.
보안 계층은 인증 결과를 애플리케이션이 사용할 수 있는 형태로 축약해 전달한다.

허용:

- 현재 사용자 식별자 전달
- 현재 사용자 권한 정보 전달
- 인증 여부 또는 인증된 주체 정보 전달

지양:

- Controller에서 토큰 직접 해석
- Service에서 헤더, 쿠키, 세션 객체 직접 해석
- Service에서 인증 방식별 분기 처리

즉, 보안 정보는 "누가 요청했는가", "무슨 권한이 있는가" 수준으로 전달하고,
전송 매체나 인증 메커니즘의 세부 구현은 보안 계층에 남긴다.

---

## 7. 인증 실패와 인가 실패를 구분한다

- 인증 실패: 로그인되지 않았거나 인증 정보가 유효하지 않은 경우 → `401`
- 인가 실패: 인증은 되었지만 필요한 권한이 없는 경우 → `403`

규칙:

- 인증 실패와 인가 실패는 구분된 응답과 로깅으로 처리한다.
- 인증 실패 응답에 내부 검증 세부를 과도하게 노출하지 않는다.

---

## 8. 권한 검사의 계층을 나눈다

- 보안 계층: 공개/보호 엔드포인트 구분, 인증 필요 여부, 역할 기반 접근 제한
- Service/도메인 계층: 특정 데이터의 소유권, 업무 상태, 조직 범위 같은 업무 맥락 권한 검사

예:
- 보안 계층에서 관리자 전용 기능 차단
- Service에서 자신의 리소스만 수정 가능한지 판단

---

## 9. 금지 규칙

- 인증과 인가를 같은 개념처럼 다루지 않는다.
- `permitAll`을 편의상 넓게 열지 않는다.
- 민감정보를 로그, 예외, 응답에 그대로 노출하지 않는다.
- Controller나 Service가 토큰, 쿠키, 세션 세부 구현에 강하게 결합되지 않게 한다.
- 보안 설정 안에 업무 규칙이나 데이터별 권한 판단을 과도하게 넣지 않는다.
- 인증 방식 변경이 Controller나 Service 전반 수정으로 이어지는 구조를 만들지 않는다.

---

## 10. 한 줄 요약

- 인증과 인가를 분리한다.
- 민감정보는 저장, 출력, 전달 전 과정에서 최소 노출로 다룬다.
- 기본은 보호, 필요한 경로만 제한적으로 공개한다.
- 보안 설정은 접근 제어의 틀을 담당하고, Controller/Service에는 축약된 사용자 정보만 전달한다.
- 일반 접근 제어와 업무 맥락 권한 검사는 계층을 나눠 처리한다.
