# EPIC-02 회사 프로필 시나리오

대상 화면: `/company/profile` (`CompanyProfilePage`)

---

## 시나리오 1: 골든 패스 — 신규 프로필 작성 및 저장

- 사전조건: 로그인된 상태, 아직 회사 프로필을 등록한 적 없는 계정
- 절차:
  1. `/` 에서 "회사 프로필" 링크 클릭 → `/company/profile` 진입
  2. 기본 정보 섹션에서 "회사명"에 값 입력 (필수값)
  3. 지역 드롭다운에서 하나 선택
  4. 기술 태그 섹션에서 태그 1개 이상 선택
  5. 사업 분야 섹션에서 항목 1개 이상 선택
  6. "보유 인증"에 값 입력 후 "추가" 클릭
  7. "프로젝트 경험"에 "프로젝트 구분"과 "프로젝트 설명"을 모두 입력 후 "추가" 클릭
  8. "입찰 선호 조건"에서 항목 1개 이상 설정
  9. 하단 "저장" 버튼 클릭
- 기대 결과:
  - 1번: 로딩 중에는 "불러오는 중..." 표시 후, 신규 프로필이라 빈 폼이 렌더링된다
  - 6번: 입력한 인증명이 태그 형태로 목록에 추가되고 입력창은 비워진다
  - 7번: 입력한 프로젝트 구분·설명이 "구분 · 설명" 형태로 목록에 추가되고 두 입력창은 비워진다. "프로젝트 구분"과 "프로젝트 설명" 중 하나라도 비어 있으면 추가되지 않는다.
  - 9번: 저장 버튼이 "저장 중..."으로 바뀌었다가, 성공 시 "저장되었습니다." 토스트가 표시된다. 새로고침해도 인증·프로젝트 경험이 그대로 남아있다.

## 시나리오 2: 골든 패스 — 기존 프로필 조회 및 수정 (인증/프로젝트 경험 삭제 포함)

- 사전조건: 이미 프로필이 저장되어 있는 계정으로 로그인 (시나리오 1에서 인증·프로젝트 경험을 추가해둔 상태)
- 절차:
  1. `/company/profile` 진입
  2. 저장돼 있던 값들이 각 필드에 채워져 있는지 확인 (회사명, 지역, 기술 태그, 인증, 프로젝트 경험 등)
  3. "강점" 텍스트를 수정
  4. "프로젝트 경험" 목록에서 항목의 "×" 버튼 클릭
  5. "저장" 클릭
- 기대 결과:
  - 2번: 이전에 저장한 값이 그대로 폼에 반영되어 있다
  - 4번: 클릭한 프로젝트 경험 항목이 화면에서 즉시 사라진다 (저장 전, 클라이언트 상태만 변경)
  - 5번: 저장 성공 토스트가 표시되고, 새로고침해도 강점 수정 내용은 유지되면서 삭제한 프로젝트 경험 항목은 다시 나타나지 않는다

## 시나리오 3: 필수값 미입력 (클라이언트 검증 실패)

- 사전조건: `/company/profile` 진입한 상태
- 절차:
  1. "회사명" 필드를 완전히 빈 값으로 두고(한 번도 입력하지 않은 상태) "저장" 클릭
  2. "회사명" 필드에 공백 문자만(예: 스페이스 3칸) 입력하고 "저장" 클릭
- 기대 결과:
  - 1번: `input`에 `required` 속성이 있어 **브라우저 네이티브 필수값 검증이 먼저 개입**한다. 폼의 `onSubmit`(및 앱의 커스텀 검증)은 아예 실행되지 않고, 브라우저 기본 툴팁(예: "Please fill out this field.", 영어)만 표시된다. 앱이 의도한 "회사명을 입력해주세요." 토스트는 이 경우 뜨지 않는다.
  - 2번: 공백은 네이티브 `required` 검증을 통과하므로 `onSubmit`이 실행되고, API 요청 없이 "회사명을 입력해주세요." 에러 토스트가 표시된다.
  - (참고) 1번 동작은 실제 화면에서 확인된 사실이며, 앱이 전부 한글 UX인데 이 경로만 영어 브라우저 툴팁이 뜨는 점은 제품/코드 관점에서 개선 여지가 있다고 판단됨 — 이 문서는 현재 동작을 있는 그대로 기록한 것이고, 수정 여부는 별도 판단 필요.

## 시나리오 4: 프로필 조회 실패

- 사전조건: 백엔드가 프로필/코드 조회 API에서 에러를 반환하도록 재현
- 절차:
  1. `/company/profile` 접속
- 기대 결과: "프로필을 불러오지 못했습니다." 안내가 표시되고 폼은 렌더링되지 않는다

## 시나리오 5: 저장 API 실패

- 사전조건: 회사명 등 필수값은 채운 상태에서, 저장 요청이 실패하도록 재현 (예: Playwright MCP로 저장 API 응답을 5xx로 강제)
- 절차:
  1. 필수값을 채우고 "저장" 클릭
- 기대 결과: 서버가 내려준 에러 메시지(또는 "저장에 실패했습니다.")가 에러 토스트로 표시되고, 입력했던 폼 값은 그대로 유지된다

## 시나리오 6: 재계산 상태 버튼 — 상태별 표시

- 사전조건: 이미 프로필이 저장되어 있는 계정으로 로그인. Playwright MCP에는 네트워크 응답을 가로채 값을 바꿔치는 도구가 없으므로, 로컬 DB(`match_calculation_status` 테이블)를 `docker exec bidradar-postgres psql -U bidradar -d bidradar -c "update match_calculation_status set status = '<값>', updated_at = now() - interval '<n> minutes' where company_id = <해당 계정의 company_id>;"`로 직접 갱신해 상태를 재현한다.
- 절차 및 기대 결과 (각각 DB 갱신 후 `/company/profile`을 새로고침해 확인):
  1. 행 자체가 없음(최초 저장 전) → 버튼이 렌더링되지 않음
  2. `status = 'IN_PROGRESS'`, `updated_at`이 5분 이내 → 버튼 비활성화, "재계산 중입니다." (2026-08-03 검증 완료 — 프로필 저장 직후 자동 트리거로 실제 재현됨)
  3. `status = 'IN_PROGRESS'`, `updated_at`이 5분 초과 → 버튼 활성화, "재계산이 예상보다 오래 걸리고 있습니다. 재계산을 다시 시작해 주세요."
  4. `status = 'FAILED'` → 버튼 활성화, "재계산에 실패했습니다." (2026-08-03 검증 완료)
  5. `status = 'DONE'` → 버튼 비활성화, "재계산이 완료되었습니다." (2026-08-03 검증 완료 — 자동 트리거 후 폴링으로 전이되는 것까지 실제 확인됨)

## 시나리오 7: 재계산 버튼 클릭 — 재시도 성공 및 폴링에 따른 상태 갱신

- 사전조건: 시나리오 6의 방법으로 `match-status`를 `FAILED`로 만든 계정
- 절차:
  1. "재계산" 버튼 클릭
  2. 약 5초 간격으로 자동 재조회되는 것을 확인 (버튼 문구가 "재계산 중입니다."로 바뀜)
  3. 실제 재계산이 완료될 때까지 대기
- 기대 결과 (2026-08-03 전체 검증 완료):
  - 1번: `POST /companies/me/match-status/retry`가 호출되고, 클릭 즉시 별도 토스트 없이 버튼이 비활성화되고 "재계산 중입니다."로 바뀐다 (성공 피드백은 버튼 상태 변화 자체)
  - 3번: `DONE`으로 전이되면 별도 알림 없이 버튼이 "재계산이 완료되었습니다."로 바뀌고, 공고 목록 캐시(`['bids']`)가 무효화되어 목록으로 돌아가면 새로 `GET /bids` 요청이 발생한다

## 시나리오 8: 재계산 버튼 클릭 실패 (경쟁 상태로 인한 거부)

- 사전조건: `match-status`가 신선한 `IN_PROGRESS`이거나 `DONE`인 상태(재시도가 서버에서 거부되는 상태)에서, 브라우저 개발자 도구나 curl로 `POST /companies/me/match-status/retry`를 직접 호출해 409(`MATCH_CALCULATION_RETRY_NOT_ALLOWED`)를 확인하는 방식으로 재현 (버튼 자체는 이 상태에서 비활성화되어 있어 화면 클릭으로는 도달하지 않음 — 클라이언트 판단과 서버 판단 사이 경쟁 상태 대비용 방어 로직 확인 목적)
- 절차:
  1. 위 방법으로 API를 직접 호출
- 기대 결과: 서버가 내려준 에러 메시지가 에러 토스트로 표시되고, 버튼은 클릭 전 상태 표시로 되돌아온다

## 시나리오 9: 이미 완료된 상태에서 프로필을 재저장 — 재계산 추적 재시작

- 사전조건: `match-status`가 이미 `DONE`으로 캐시되어 있는(=이전에 한 번 재계산이 끝난) 계정. Codex 리뷰(PR #46)에서 지적된 회귀 — `useSaveCompanyProfile`이 회사 쿼리만 갱신하고 `match-status` 쿼리는 그대로 둬서, 캐시가 `DONE`인 채로 재저장하면 폴링 조건(`status === 'IN_PROGRESS'`)이 충족되지 않아 새 재계산의 `DONE` 전이를 영영 관찰하지 못하는 문제였다.
- 절차:
  1. `/company/profile` 진입 (버튼이 "재계산이 완료되었습니다."로 표시됨을 확인)
  2. 아무 필드나 값을 바꾸고 "저장" 클릭
- 기대 결과 (2026-08-03 검증 완료): 저장 직후 별도 조작 없이 버튼이 즉시 "재계산 중입니다."(비활성화)로 바뀌고, 이후 폴링으로 다시 "재계산이 완료되었습니다."로 전이되며 공고 목록 캐시가 무효화된다 — 화면이 계속 이전 "완료" 상태로 멈춰 있지 않는다.

## 시나리오 10: 반복되는 IN_PROGRESS 응답에서도 5분 경과 판정이 저절로 갱신됨

- 사전조건: Codex 리뷰(PR #46)에서 지적된 문제 — 동일한 `status`/`updatedAt`이 반복되면 TanStack Query의 structural sharing으로 데이터 참조가 안 바뀌어 컴포넌트가 리렌더되지 않고, `new Date()` 기준 stale 판정이 최초 렌더 시각에 멈춰 있던 버그. `match_calculation_status.updated_at`을 (호스트 로컬 시각 기준) 현재로부터 4분 50초 전으로 직접 갱신해 재현한다 (`docker exec` psql — DB 컨테이너의 `now()`는 UTC라 호스트 로컬 시각과 다를 수 있으니 반드시 `date` 명령으로 구한 호스트 로컬 시각을 리터럴로 넣을 것).
- 절차:
  1. `/company/profile` 진입, 버튼이 "재계산 중입니다."(비활성화)로 보이는지 확인
  2. 화면을 조작하지 않고 20초 이상 대기 (5분 경계를 넘길 때까지)
- 기대 결과 (2026-08-03 검증 완료): 아무 상호작용 없이도 버튼이 "재계산이 예상보다 오래 걸리고 있습니다. 재계산을 다시 시작해 주세요."(활성화)로 저절로 바뀐다.

## 시나리오 11: 상태 조회 실패 시 "다시 확인" 버튼

- 사전조건: `GET /companies/me/match-status`가 실패하도록 재현 (Playwright MCP에는 특정 요청만 골라 실패시키는 네트워크 가로채기 도구가 없어, 백엔드를 일시 중지하는 등 요청 자체가 실패하는 상황으로 재현해야 한다 — 아직 실제 재현은 못 했고 코드/타입체크로만 확인됨, 아래는 기대 동작 명세)
- 절차:
  1. `/company/profile` 진입
- 기대 결과: 버튼 자리에 "상태를 불러오지 못했습니다." 문구와 "다시 확인" 버튼이 표시된다. "다시 확인" 클릭 시 재계산 요청(`retry`)이 아니라 상태 조회(`GET /match-status`)만 다시 호출된다.
