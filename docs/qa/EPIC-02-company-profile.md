# EPIC-02 회사 프로필 시나리오

대상 화면: `/company/profile` (`CompanyProfilePage`)

---

## 시나리오 1: 골든 패스 — 신규 프로필 작성 및 저장

- 사전조건: 로그인된 상태, 아직 회사 프로필을 등록한 적 없는 계정
- 절차:
  1. `/` 에서 "회사 프로필" 링크 클릭 → `/company/profile` 진입
  2. 기본 정보 섹션에서 "회사명"에 값 입력 (필수값)
  3. 지역 드롭다운에서 하나 선택
  4. 기술 태그 섹션에서 태그 1개 이상 선택
  5. 사업 분야 섹션에서 항목 1개 이상 선택
  6. "보유 인증"에 값 입력 후 "추가" 클릭
  7. "프로젝트 경험"에 "프로젝트 구분"과 "프로젝트 설명"을 모두 입력 후 "추가" 클릭
  8. "입찰 선호 조건"에서 항목 1개 이상 설정
  9. 하단 "저장" 버튼 클릭
- 기대 결과:
  - 1번: 로딩 중에는 "불러오는 중..." 표시 후, 신규 프로필이라 빈 폼이 렌더링된다
  - 6번: 입력한 인증명이 태그 형태로 목록에 추가되고 입력창은 비워진다
  - 7번: 입력한 프로젝트 구분·설명이 "구분 · 설명" 형태로 목록에 추가되고 두 입력창은 비워진다. "프로젝트 구분"과 "프로젝트 설명" 중 하나라도 비어 있으면 추가되지 않는다.
  - 9번: 저장 버튼이 "저장 중..."으로 바뀌었다가, 성공 시 "저장되었습니다. 적합도 재계산을 요청했습니다." 토스트가 표시된다. 새로고침해도 인증·프로젝트 경험이 그대로 남아있다.

## 시나리오 2: 골든 패스 — 기존 프로필 조회 및 수정 (인증/프로젝트 경험 삭제 포함)

- 사전조건: 이미 프로필이 저장되어 있는 계정으로 로그인 (시나리오 1에서 인증·프로젝트 경험을 추가해둔 상태)
- 절차:
  1. `/company/profile` 진입
  2. 저장돼 있던 값들이 각 필드에 채워져 있는지 확인 (회사명, 지역, 기술 태그, 인증, 프로젝트 경험 등)
  3. "강점" 텍스트를 수정
  4. "프로젝트 경험" 목록에서 항목의 "×" 버튼 클릭
  5. "저장" 클릭
- 기대 결과:
  - 2번: 이전에 저장한 값이 그대로 폼에 반영되어 있다
  - 4번: 클릭한 프로젝트 경험 항목이 화면에서 즉시 사라진다 (저장 전, 클라이언트 상태만 변경)
  - 5번: 저장 성공 토스트가 표시되고, 새로고침해도 강점 수정 내용은 유지되면서 삭제한 프로젝트 경험 항목은 다시 나타나지 않는다

## 시나리오 3: 필수값 미입력 (클라이언트 검증 실패)

- 사전조건: `/company/profile` 진입한 상태
- 절차:
  1. "회사명" 필드를 완전히 빈 값으로 두고(한 번도 입력하지 않은 상태) "저장" 클릭
  2. "회사명" 필드에 공백 문자만(예: 스페이스 3칸) 입력하고 "저장" 클릭
- 기대 결과:
  - 1번: `input`에 `required` 속성이 있어 **브라우저 네이티브 필수값 검증이 먼저 개입**한다. 폼의 `onSubmit`(및 앱의 커스텀 검증)은 아예 실행되지 않고, 브라우저 기본 툴팁(예: "Please fill out this field.", 영어)만 표시된다. 앱이 의도한 "회사명을 입력해주세요." 토스트는 이 경우 뜨지 않는다.
  - 2번: 공백은 네이티브 `required` 검증을 통과하므로 `onSubmit`이 실행되고, API 요청 없이 "회사명을 입력해주세요." 에러 토스트가 표시된다.
  - (참고) 1번 동작은 실제 화면에서 확인된 사실이며, 앱이 전부 한글 UX인데 이 경로만 영어 브라우저 툴팁이 뜨는 점은 제품/코드 관점에서 개선 여지가 있다고 판단됨 — 이 문서는 현재 동작을 있는 그대로 기록한 것이고, 수정 여부는 별도 판단 필요.

## 시나리오 4: 프로필 조회 실패

- 사전조건: 백엔드가 프로필/코드 조회 API에서 에러를 반환하도록 재현
- 절차:
  1. `/company/profile` 접속
- 기대 결과: "프로필을 불러오지 못했습니다." 안내가 표시되고 폼은 렌더링되지 않는다

## 시나리오 5: 저장 API 실패

- 사전조건: 회사명 등 필수값은 채운 상태에서, 저장 요청이 실패하도록 재현 (예: Playwright MCP로 저장 API 응답을 5xx로 강제)
- 절차:
  1. 필수값을 채우고 "저장" 클릭
- 기대 결과: 서버가 내려준 에러 메시지(또는 "저장에 실패했습니다.")가 에러 토스트로 표시되고, 입력했던 폼 값은 그대로 유지된다

## 시나리오 6: 저장은 성공, 적합도 재계산 요청만 실패 (부분 실패)

- 사전조건: `recalculated`는 백엔드 응답 필드가 아니라 `useSaveCompanyProfile`이 `POST /companies/me/recalculate` 호출의 성공 여부를 보고 프런트에서 만드는 값이다. 이 시나리오를 재현하려면 저장 `PUT /companies/me`는 정상 응답하도록 두고, 재계산 `POST /companies/me/recalculate`만 네트워크 오류 또는 5xx로 강제한다 (예: Playwright MCP로 해당 요청 경로만 골라 실패 응답을 반환하도록 가로채기).
- 절차:
  1. 필수값을 채우고 "저장" 클릭
- 기대 결과: "저장은 완료되었지만 재계산 요청에 실패했습니다." 토스트가 (성공이 아닌) 에러 스타일로 표시된다
